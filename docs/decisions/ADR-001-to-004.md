# ADR-001: Product Scope — Digital Rent Register Only

## Status

**Accepted**

## Context

The Indian market has many property management tools (NoBroker, MyGate, ApnaComplex) that try to be everything: society management, visitor management, maintenance, accounting, and rent. These are complex, expensive, and often unsuitable for small landlords who just want to know who has paid rent.

Our target user currently uses a physical register, notebook, or WhatsApp. They need a digital replacement for the register, not an enterprise platform.

## Decision

RentBook is **a digital rent register and nothing more** in its MVP phase.

The product scope is limited to:
1. Recording properties, units, and tenants
2. Tracking monthly rent obligations
3. Recording payments
4. Viewing collection status
5. Sending simple reminders

All other features (maintenance, billing, accounting, legal, marketplace) are explicitly out of scope and must not influence architecture decisions.

## Consequences

**Positive**:
- Small codebase, faster development
- Simple to understand and use
- Lower maintenance burden
- Clear product identity

**Negative**:
- Users who want a complete solution will look elsewhere
- Revenue opportunities from adjacent features are deferred

**Mitigated by**:
- Clean architecture allows expansion when validated by real demand
- Phase 2/3 roadmap exists for planned expansion

# ADR-002: Rent Record Generation — On-Demand

## Status

**Accepted**

## Context

Monthly rent records need to be created for each active tenant. There are several approaches:

### Option A: Background Job (Cron)
A scheduled job runs on the 1st of each month and creates rent records for all active tenants.

- ✅ Ensures records exist at month start
- ❌ Requires background job infrastructure (Celery, APScheduler, etc.)
- ❌ If job fails, no records exist; need monitoring and retry logic
- ❌ Adds operational complexity for a small MVP

### Option B: Eager Creation on Tenant Add
Create rent records for the current month (and potentially future months) when a tenant is added.

- ✅ Records exist immediately
- ❌ What if tenant is added mid-month? How many months ahead?
- ❌ Rent amount changes require updating future records
- ❌ Over-generates records that may never be needed

### Option C: On-Demand Generation (Chosen)
Rent records are created when the owner views data for a specific month (dashboard, rent page). The system checks if records exist for active tenants in that month and creates missing ones.

- ✅ No background infrastructure needed
- ✅ Records are created with current rent amount at view time
- ✅ Naturally handles mid-month tenant additions
- ✅ No over-generation of future records
- ❌ First view of a month is slightly slower (one-time record creation)
- ❌ If owner never opens the app, records aren't created (acceptable — no one is checking rent)

### Option D: Purely Manual
Owner manually creates each month's rent record.

- ✅ Maximum control
- ❌ Tedious for 20+ tenants
- ❌ Easy to forget
- ❌ Defeats the purpose of automation

## Decision

**Option C: On-Demand Generation**

When the owner accesses rent data for a specific month/year (via dashboard or rent page):
1. Query all active tenants across owner's properties
2. For each active tenant, check if a rent record exists for that month/year
3. If not, create one with:
   - `expected_amount_paise` = unit's current `monthly_rent_paise`
   - `due_date` = `{year}-{month}-{unit.rent_due_day}`
4. Use database `INSERT ... ON CONFLICT DO NOTHING` to prevent duplicates
5. Return all rent records for the month

### Edge Cases Handled

| Case | Behavior |
|------|----------|
| Tenant added mid-month | Record created on next dashboard/rent view |
| Tenant deactivated | No new record created (status = INACTIVE) |
| Rent amount changed | New records use new amount; existing records unchanged |
| Owner views same month twice | Duplicate prevented by unique constraint |
| Vacant unit | No record created (no active tenant) |

## Consequences

- Simple implementation
- No background job dependencies
- First dashboard load each month is slightly slower (imperceptible for < 100 tenants)
- Rent records are guaranteed to exist once the owner has viewed the month

# ADR-003: Payment Model — Separate Payments Table

## Status

**Accepted**

## Context

Should payment be a field on the rent record or a separate entity?

### Option A: Payment Fields on Rent Record
Add `paid_amount`, `paid_date`, `payment_method` directly to the rent_records table.

- ✅ Simpler schema
- ❌ Cannot handle partial/split payments
- ❌ Cannot handle payment corrections without losing original data
- ❌ Only one payment per rent record

### Option B: Separate Payments Table (Chosen)
A `payments` table with a foreign key to `rent_records`.

- ✅ Supports multiple payments per rent record (partial payments)
- ✅ Each payment has its own date, method, and amount
- ✅ Payments can be voided without destroying data
- ✅ Total paid = SUM(payments.amount_paise) WHERE is_void = FALSE
- ❌ Slightly more complex queries (JOIN + aggregate)

## Decision

**Option B: Separate Payments Table**

A rent record can have 0 or more payments. Rent status is computed from the sum of non-voided payments vs. expected amount.

This design handles:
- Full payment in one transaction
- Partial payments (tenant pays in installments)
- Payment corrections (void old, create new)
- Overpayments (detectable via total > expected)

## Consequences

- Dashboard queries require a JOIN with payments and aggregation
- But this is straightforward SQL and performs well at MVP scale
- Financial integrity is preserved — payments are never deleted

# ADR-004: Notification Strategy — Manual WhatsApp Deep Links

## Status

**Accepted**

## Context

Landlords need to remind tenants about rent. Options considered:

### Option A: WhatsApp Business API
Automated messages via official API.

- ✅ Fully automated
- ❌ Requires business verification (weeks)
- ❌ Per-message cost
- ❌ Complex integration
- ❌ Overkill for MVP

### Option B: SMS Gateway (MSG91, Twilio)
Send SMS reminders.

- ✅ Works on all phones
- ❌ Per-message cost
- ❌ SMS fatigue — users ignore SMS
- ❌ Integration complexity

### Option C: WhatsApp Deep Links (Chosen)
Generate a `wa.me` URL with pre-filled message. Owner taps link → WhatsApp opens → owner taps send.

- ✅ Zero integration cost
- ✅ Zero per-message cost
- ✅ Works with any WhatsApp account (no business verification)
- ✅ Owner controls when/if to send
- ✅ Tenant receives from a known number (the landlord's)
- ❌ Requires manual action (owner must tap send)
- ❌ Cannot confirm delivery programmatically

### Option D: Email
Send email reminders.

- ✅ Free
- ❌ Many Indian tenants don't check email for rent matters
- ❌ Low engagement rate

## Decision

**Option C: WhatsApp Deep Links for MVP**

The reminder flow is:
1. System identifies eligible tenants (DUE or OVERDUE)
2. Owner taps "Remind"
3. System generates WhatsApp URL with pre-filled message
4. WhatsApp opens on owner's device
5. Owner taps Send
6. System records reminder attempt

This matches how landlords already communicate — via WhatsApp — but adds convenience (pre-filled message) and tracking (reminder history).

## Consequences

- No messaging infrastructure to build or maintain
- No per-message costs
- Owner remains in full control
- Phase 2 can add WhatsApp Business API or SMS when validated
